# Проблема - M2, ядро

[⌂ index](index.md)

## Проблема, как она поставлена

Документация, контент-репозиторий с golden sample и прототип UI готовы, а кода ядра нет. Веха M2 из [roadmap](../../roadmap.md) - headless-пакеты `core`, `srs` и `content-fs` и CLI `check`, `build`, `render`, `simulate`. Готово, когда тесты replay и property-тесты зелёные, а симуляция бэклога проходит. Требования вехи: FR-204, FR-208, FR-307, NFR-04, NFR-05, NFR-14.

## У кого эта проблема

- **Автор контента** - единственный пользователь системы. Он пишет темы и карточки в `wastech-learn-content` и хочет знать, что контент корректен не только по mdlint.
- **Будущие хосты** - MCP-сервер (M3), локальный сервер и приложение (M4). Им нужны готовые схемы, проверка `check`, content bundle, replay и очередь, а не собственная логика.

## Текущая ситуация

- Контент проверяет только wastech-mdlint. Правила второго уровня из [mdlint-policy](../../quality/mdlint-policy.md) (длина вопроса и ответа, пропуски cloze, уникальность `id`, свежесть SVG, привязка к summary, расхождение пресета) не проверяет ничто.
- Диаграммы рендерит временный скрипт `scripts/render-diagrams.mjs` в контент-репозитории.
- Прототип собирает данные своим скриптом `build-data.mjs`. Интервалы, R и статистика в нём демонстрационные: FSRS нигде не считается.
- Журнал `reviews/` пуст, и записывать в него нечем. Формат события описан в [review-log](../../content/review-log.md), но не проверен кодом.

## Почему сейчас

- Это следующий шаг roadmap. Блокирующие вопросы Q-02, Q-03 и Q-04 закрыты 2026-11-26.
- M3 без ядра не начать: каждая запись через MCP должна проходить mdlint и `check` (FR-108).
- M4 не начать без bundle, replay и очереди: UI получает контент только из bundle, а состояние - через `ReviewStore`.
- ts-fsrs 6 вышел недавно и сменил API. Чем раньше адаптер и replay закреплены тестами, тем дешевле следующие обновления (R-01).

## Сигналы и факты

- Golden sample: 3 темы, 30 карточек, языки en, ru и pl, 0 ошибок mdlint.
- Дубль `id` mdlint не ловит - это записано в mdlint-policy как задача `check`.
- `ts-fsrs@6.0.1` проверен: `DefaultScheduler` с FSRS-7, шаги `1m, 10m` / `10m` с `allowModelOverride`, детерминированный fuzz с сидом `cardId + reps`, `Reschedule.replay()`.
- Критерий выхода MVP: 14-дневный бэклог разбирается сессиями по 15 минут не дольше 5 дней.

## Ограничения, заданные заранее

- Архитектура из [.rules/architecture.md](../../../.rules/architecture.md): `core` и `srs` чистые и не зависят друг от друга, без Node API, часов и случайности. IO только в `content-fs`, хосты тонкие.
- Инварианты данных: Markdown не хранит состояние планирования, журнал append-only со своим файлом на writer, `id` карточки случайный и стабильный, replay побайтно детерминирован.
- Планировщик - `ts-fsrs@6.0.1` с параметрами из `learn.config.json` ([srs](../../scheduling/srs.md)).
- Node ≥ 24.17, ESM, TypeScript 6.0, npm workspaces `packages/*`, Vitest и fast-check.
- Без вызовов моделей, ключей и телеметрии.
