# ADR-0015: Пакет `session` и replay в клиенте

## Контекст

В M4 у повторения появляется второй хост — приложение в браузере. Логика ответа на карточку живёт в `content-fs/study.ts` и `load.ts`: перевод значений `core` в порты `srs`, сборка события `review` (`durMs`, `contentHash`, `sched`), правило leech с автоматическим `suspend`, отмена оценки вместе с её `suspend`. `content-fs` работает на Node, браузер его не импортирует ([components](../architecture/components.md)).

Правило «логика второго хоста — в `core`, `srs` или `content-fs`» здесь не срабатывает: `content-fs` — Node, а `core` и `srs` не зависят друг от друга. Событию нужна схема `core`, правилу leech и прогнозу интервалов — планировщик `srs`.

[ADR-0007](0007-local-server-phase-1.md) предполагал кэш replay в `node:sqlite` на сервере. Бенчмарк M2 (NFR-05) проходит без кэша, а в фазе 2 у Capacitor нет Node.

## Решение

- Новый пакет `@wastech-learn/session`: чистый, без Node API, часов и случайности (`now` и RNG — входы), зависит только от `core` и `srs`.
- Он владеет: переводом значений `core` в порты `srs` (`toQueueCards` для модели и для content bundle, `toReplayEvents`, `toSrsConfig`), сборкой событий `review`, `undo`, `suspend`, `unsuspend`, `reset`, правилом leech, прогнозом интервалов четырёх кнопок, движком сессии (режим, очередь в ходе сессии, отмена, bury) и её итогами.
- Порядок зависимостей: `core`, `srs` → `session` → `content-fs` → хосты (`cli`, `mcp-server`, `server`); `app` → `core`, `srs`, `session`. Границы задаёт `eslint.config.js`.
- Квиз MCP и приложение собирают события одними функциями: событие `mcp` и событие `web` различаются только `writer` и `device`.
- Replay, очередь и метрики считает клиент: полный replay при загрузке и после внешнего изменения журнала, дальше по одному событию через `createReplayer`. Сервер отдаёт bundle и события и не держит состояния планировщика.
- Кэша replay в `node:sqlite` в фазе 1 нет. К нему возвращаются, если replay реального журнала в браузере станет дольше 5 с.

## Альтернативы

- **Логика в `srs`, `srs` импортирует `core`.** Ломает независимость двух чистых пакетов; каждый потребитель планировщика тянул бы Zod, unified и Shiki.
- **Логика в `core`, `core` импортирует `srs`.** Та же связь в обратную сторону.
- **Копия в `app`.** Два места для правила leech и сборки события: квиз и приложение разойдутся при первой правке.
- **Состояние считает сервер.** Маршрут на каждый экран, а в фазе 2 (Capacitor, облако) логику всё равно переносить в клиент.
- **Кэш `node:sqlite` сразу.** Ещё один слой с инвалидацией без измеренной нужды; браузер им не пользуется.

## Последствия

- Шестой пакет. `content-fs` переходит на `session`, его публичный API для `mcp-server` не меняется.
- Один код в Node и в браузере делает проверяемым NFR-04: состояние после сессии в клиенте совпадает с replay того же журнала в Node.
- `session` тестируется против прямых вызовов ts-fsrs, движок — property-тестом «инкрементальный replay равен полному».
- Если replay в браузере станет узким местом, он уходит в Web Worker; Node API для этого не нужны.
- В «Последствиях» ADR-0007 появляется строка о том, что кэш `node:sqlite` в фазе 1 отменён этим ADR.
